# Plan: Fix Crawling Issue for Stuck Jobs

## Problem Summary

Jobs created via the crawl pipeline get stuck at `CRAWLING` status and never transition to `PROCESSING`, `AUDITING`, or `COMPLETED`. Example: Job `782a1d6f-5be3-45e6-b82e-80ed82450078`.

---

## Root Cause Analysis

After thorough investigation of the codebase, the following issues were identified in the crawl pipeline:

### Issue 1: No Job Status Update After Pipeline Completes (Critical)

**File**: `rag-pipline/apps/api/src/workers/crawl_tasks.py` (lines 124-149)

The `finalize_crawl` Celery task only saves a manifest file and returns data — it **never updates the job status in the database**. The job is set to `CRAWLING` in the API router (`jobs.py` line 44) but nothing ever changes it to `COMPLETED` or `FAILED`.

### Issue 2: No Error Handling for Failed Tasks (Critical)

When any task in the Celery chain or chord fails, the error propagates but the job status is never updated to `FAILED`. The chain continues to the next task even if a previous task failed, leaving the job in an indefinite state.

### Issue 3: Chord Pattern Silent Failure (High)

The `_fan_out_and_finalize` task uses Celery's `chord` pattern (line 179). If any task in the chord group fails or hangs, the error callback (`finalize_crawl`) **never fires** because chords wait for ALL group tasks to complete. This is a known Celery limitation — a single failed or hung task in a chord prevents the callback from executing.

### Issue 4: No Task Timeouts (Medium)

None of the Celery tasks have a `time_limit` set. If a website hangs during fetch (e.g., network timeout, Playwright stuck waiting for `networkidle`), the task can run indefinitely, blocking the worker.

### Issue 5: No Heartbeat/Status Updates (Low)

The `task_track_started=True` setting exists in `celery_app.py` but tasks don't report progress, making it impossible to tell if a task is still running or truly stuck.

### Phase 1: Add Sync DB Status Update to `finalize_crawl`

**File**: `rag-pipline/apps/api/src/workers/crawl_tasks.py`

### Phase 2: Error Handling via Base Task Class

**What to remove**: The `task_failure` signal approach is broken. The signal fires for every task across all Celery apps in the process, and the handler recovers `job_id` by string-splitting the `task_id` — this is unreliable and will silently fail in most cases.

**How to rewrite it**: Use a shared base task class with `on_failure` overridden. This gives direct access to the task's `kwargs`, including `job_id`, without any string parsing:

**File**: `rag-pipline/apps/api/src/workers/crawl_tasks.py`

```python
from celery import Celery
from sqlalchemy.orm import Session
from celery.exceptions import SoftTimeLimitExceeded

from src.database import sync_engine
from src.models.chunk import IngestionJob, JobStatus

def _update_job_status_sync(job_id: str, status: JobStatus):
    """Synchronously update job status in the database."""
    try:
        with Session(sync_engine) as db:
            job = db.get(IngestionJob, job_id)
            if job:
                job.status = status
                db.commit()
    except Exception as e:
        logger.error("sync_status_update_error", job_id=job_id, status=status.value, error=str(e))


class CrawlBaseTask(celery_app.Task):
    """Base task class that updates job status on failure."""
    abstract = True

    def on_failure(self, exc, task_id, args, kwargs, einfo):
        job_id = kwargs.get("job_id") if kwargs else (args[1] if len(args) > 1 else None)
        if job_id:
            _update_job_status_sync(job_id, JobStatus.FAILED)
        super().on_failure(exc, task_id, args, kwargs, einfo)

    def on_success(self, result, task_id, args, kwargs):
        # Optionally update to PROCESSING or leave for finalize_crawl
        super().on_success(result, task_id, args, kwargs)
```

### Phase 3: Fix the Chord Pattern with `on_error` Callback

**What to correct**: Replacing the chord with `group(...) | callback` is not a fix — it is still a chord. In Celery, piping a `group` into a task with `|` creates a chord internally. The plan removes nothing; it just rewrites the chord in different syntax while losing the explicit error callback.

The real problem with the current chord is the absence of an `on_error` (link_error) callback. Fix it by adding one:

**File**: `rag-pipline/apps/api/src/workers/crawl_tasks.py`

```python
@celery_app.task(bind=True, name="crawl.handle_chord_error")
def handle_crawl_chord_error(self, result=None, exc=None, task_id=None, args=None):
    """Handle chord member failures and update job status."""
    # Extract job_id from the result dict
    if isinstance(result, dict):
        job_id = result.get("job_id", "unknown")
    else:
        job_id = "unknown"
    
    logger.error(
        "chord_member_failed",
        job_id=job_id,
        error=str(exc) if exc else str(result),
        task_id=task_id,
    )
    _update_job_status_sync(job_id, JobStatus.FAILED)


@celery_app.task(bind=True, base=CrawlBaseTask, name="crawl.fan_out_and_finalize")
def _fan_out_and_finalize(self, discovery_result: dict):
    """Fan out fetch_and_convert tasks for all discovered links, then finalize."""
    job_id = discovery_result["job_id"]
    links = discovery_result["links"]

    # Create a group of fetch_and_convert tasks
    tasks = [
        fetch_and_convert_page.s(job_id, link, idx)
        for idx, link in enumerate(links)
    ]

    # Use chord with on_error callback
    callback = finalize_crawl.s(job_id=job_id)
    error_handler = handle_crawl_chord_error.s()
    
    job = chord(tasks)(callback.on_error(error_handler))
    return {"job_id": job_id, "task_count": len(links), "chord_id": str(job.id)}
```

### Phase 5: Retry Endpoint with Safety Guards

**File**: `rag-pipline/apps/api/src/routers/jobs.py`

Add three safety mechanisms:

**5a. Race condition on double-submit** — Use a conditional update to guard against concurrent retries:

```python
from sqlalchemy import update

@router.post("/jobs/{job_id}/retry", response_model=JobResponse)
async def retry_job(job_id: uuid.UUID, db: AsyncSession = Depends(get_db)):
    """Retry a stuck or failed job. Only works if job is in FAILED or CRAWLING status."""
    result = await db.execute(
        update(IngestionJob)
        .where(IngestionJob.id == job_id, IngestionJob.status.in_([JobStatus.FAILED, JobStatus.CRAWLING]))
        .values(status=JobStatus.PENDING, updated_at=func.now())
        .returning(IngestionJob)
    )
    job = result.scalar_one_or_none()
    if not job:
        raise HTTPException(
            status_code=409, 
            detail="Job is not in a retryable state (must be FAILED or CRAWLING)"
        )

    # Revoke any existing Celery tasks for this job before re-queuing
    if getattr(job, "celery_task_id", None):
        celery_app.control.revoke(job.celery_task_id, terminate=True, signal="SIGKILL")

    # Start fresh pipeline
    start_crawl_pipeline(
        job_id=str(job.id),
        url=str(job.url),
        crawl_all=job.crawl_all_docs,
    )
    job.status = JobStatus.CRAWLING
    job.celery_task_id = None  # Will be updated by the pipeline
    await db.commit()
    await db.refresh(job)
    return job
```

## New Section: Stuck Job Reaper (Celery Beat Task)

The retry endpoint only helps when a human notices a stuck job. Add a periodic beat task that runs every 15–30 minutes and marks any job stuck in `CRAWLING` for longer than a threshold as `FAILED`:

**File**: `rag-pipline/apps/api/src/workers/crawl_tasks.py` (append)

```python
from datetime import datetime, timedelta

@celery_app.task(name="crawl.reap_stuck_jobs")
def reap_stuck_jobs():
    """Periodic task to mark jobs stuck in CRAWLING for too long as FAILED."""
    threshold = datetime.utcnow() - timedelta(minutes=30)
    with Session(sync_engine) as db:
        from sqlalchemy import select
        stuck = db.execute(
            select(IngestionJob).where(
                IngestionJob.status == JobStatus.CRAWLING,
                IngestionJob.updated_at < threshold
            )
        ).scalars().all()
        for job in stuck:
            job.status = JobStatus.FAILED
            logger.warning("reaped_stuck_job", job_id=str(job.id), updated_at=str(job.updated_at))
        if stuck:
            db.commit()
        logger.info("reap_stuck_jobs_complete", reaped=len(stuck))
```

**Register in Celery beat schedule** (`celery_app.py`):

## New Section: Playwright Process Cleanup

Task timeouts will kill the Celery task but may not close the Playwright browser process, leaking memory and file descriptors over time.

**File**: `rag-pipline/apps/api/src/crawlers/fetcher.py`

Wrap browser usage in a `try/finally` block:

```python
async def fetch_with_browser(url: str, timeout: float = 60000) -> FetchResult:
    """Fetch a URL using Playwright headless Chromium (handles JS-rendered pages)."""
    browser = None
    context = None
    try:
        async with async_playwright() as p:
            browser = await p.chromium.launch(headless=True)
            context = await browser.new_context()
            page = await context.new_page()
            await page.goto(url, wait_until="networkidle", timeout=timeout)
            html = await page.content()
            return FetchResult(
                url=url, html=html, status_code=200,
                fetch_mode=FetchMode.BROWSER,
            )
    except Exception as e:
        logger.error("browser_fetch_failed", url=url, error=str(e))
        return FetchResult(
            url=url, html="", status_code=0,
            fetch_mode=FetchMode.BROWSER, error=str(e),
        )
    finally:
        # Always close browser to prevent resource leaks
        if browser:
            try:
                await browser.close()
            except Exception:
                pass  # Browser may already be closed on error
```
